# Historical Notes

## What Pixelpost Was

Pixelpost was not a general CMS that happened to show images. It was a photoblog: a small personal publishing system centered on one photograph, its time, its words, and its place in a sequence.

The README describes the project as Pixelpost 1.7.3 and points users to local docs, wiki, and forum. The bundled docs and code reflect a community-era project: template authors, addon authors, translators, forum fixes, anti-spam addons, and shared-hosting install guidance.

## Why It Felt Good

Pixelpost reduced publishing to a calm loop:

- choose a photograph
- give it a title and note
- place it in time
- optionally attach categories, tags, comments, and EXIF
- let the archive grow one image at a time

That is a very different emotional shape from a CMS dashboard or engagement feed. The site is not organized around posts competing for attention. It is organized around chronology, looking, and return visits.

## Distinctive Values

- Image-first: the photograph is the primary object.
- Chronology-first: previous/next/first/last navigation is core.
- Owner-first: self-hosted, template-editable, database-backed, portable in principle.
- Small surface area: few directories, readable PHP, plain HTML templates.
- Photographer-centric metadata: EXIF, title, notes, categories, tags, comments.
- Calm extensibility: addons hook into publishing and rendering without making the base app feel like an application platform.

## Mark II Doctrine

PixelPost Mark II should feel like:

- a durable camera body
- a field notebook
- an independent archive system

It should preserve:

- chronology
- image-first publishing
- independent ownership
- lightweight deployment
- editable templates
- portable archives
- calm publishing rhythms

It should avoid becoming:

- a social network
- a creator platform
- an engagement engine
- a framework showcase
- SaaS infrastructure
